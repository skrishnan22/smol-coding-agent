Sandbox Under the Hood

When the model runs a shell command, the harness starts it inside a box the operating system enforces. This page explains the operating-system ideas behind src/sandbox.ts, starting from zero: what the kernel is, how programs start each other, what a pipe is, and how Seatbelt says no.

What a sandbox is

A sandbox is a place where code can run, with rules about what it may touch: which files, whether it can use the network, which programs it can start. Anything outside the rules fails. The name comes from a child's sandbox, where you play freely inside the walls.

There are a few ways to build the walls.

ApproachWhere the code runsWhat stops it
Virtual machineA whole separate fake computerIt cannot see your machine at all.
Container (Docker)Your machine, in a fenced-off viewIt only sees its own files and processes.
OS policy (Seatbelt)Your real machine and real filesThe kernel refuses any request that breaks the rules.

Seatbelt is the third kind. A sandboxed process is a running program that has a Seatbelt profile (the list of rules) attached to it. Every file, network or program request it makes is checked against the profile, and so is every request from anything it starts. The harness itself has no profile, so it is not sandboxed. Only the commands it launches are.

Programs, processes and the shell

A program is a file on disk, such as /bin/cat. It does nothing by itself. A process is a program that is running right now. The same program can be running several times at once, and each run is its own process.

bash is a shell: a program whose job is to read a line of text and start the right programs for it. While it runs, it is a process like any other. cat and sed are separate programs, and each one becomes its own process when the shell starts it.

bash is not special to the sandbox. The harness runs bash -c "…" because the model writes shell syntax (pipes, &&, redirects), and bash is the program that understands it. The same wrapper could launch python script.py.

What happens in one bash call

  1. Resolve the paths
    Turn the project, temp and home folders into their real locations.
  2. Build the Seatbelt profile
    A list of allow and deny rules the kernel will enforce.
  3. Spawn the shell
    sandbox-exec applies the profile, then becomes bash.
  4. Collect its output
    stdout and stderr flow through pipes. stdin is switched off.
  5. Enforce the time limit
    After 30 seconds the process is killed.

Programs ask, the kernel decides

A program such as cat cannot read a disk by itself. Only the kernel, the core of the operating system, may touch the disk, the network and other hardware. A normal program lives in user space and asks the kernel to act for it. Each request is a system call (syscall), for example open, write or connect.

Seatbelt is a checkpoint inside the kernel. Before the kernel carries out a request from a sandboxed process, it checks that process's profile. If a rule says deny, the kernel returns an error called EPERM, which programs print as Operation not permitted. The program keeps running. Only that one request failed.

Why this beats reading the command text. cat, a Python script and a clever one-liner all end up making the same syscalls. The kernel sees the request itself, so it does not matter which program or trick produced it. That is the difference from the old read_file check, which looked at a string before acting.

Spawning, exec and inheritance

A process is a running program. Every process is started by another one, its parent. In runSandboxed, the harness (a Bun process) calls Bun.spawn, which starts sandbox-exec. That tool is Apple's launcher for Seatbelt. It attaches your profile to itself, then calls exec, which swaps a different program into the same process. The process that was sandbox-exec is now bash, and it is already sandboxed.

Children inherit three things from a parent: the sandbox, the environment variables and the open files. The sandbox part cannot be removed. A process may tighten its sandbox but never loosen it, so a command the model writes cannot switch it off.

Environment variables are named strings that every process carries, such as PATH or HOME. By default a child receives a copy of all of its parent's. Seatbelt does not restrict that channel, so the harness closes it by hand.

Default: child inherits all

  • PATH=/usr/bin:…
  • HOME=/Users/you
  • TERM=xterm-256color
  • OPENAI_API_KEY=sk-…
  • …everything else

Ours: allowlist

  • PATH
  • HOME
  • LANG
  • TERM
  • TMPDIR
  • OPENAI_API_KEY

Without the allowlist, echo $OPENAI_API_KEY would print your key into the model's context and into the log file, even though the network is blocked.

Files, pipes and stdin

To a program, every open file, pipe or device is just a number called a file descriptor. Three exist from the start: 0 is stdin (input), 1 is stdout (normal output) and 2 is stderr (errors). The parent decides where each one points.

In sandbox.ts, stdin points at /dev/null, a device that is always at end-of-file. A read returns "no more input" immediately, so a bare cat exits at once instead of waiting for you to type. Stdout and stderr point at pipes. A pipe is a small buffer inside the kernel that one process writes into and another reads from.

The harness needs the command's output so it can hand it to the model. The command and the harness are separate processes with separate memory, so the text has to travel through the kernel. A pipe is the tube it travels through: the command writes text in at one end and the harness reads it out at the other. In the middle sits a small bucket, the buffer. It holds only tens of kilobytes.

Why is there a capture function at all?

Reading does not happen by itself. The harness is given a stream, and something has to keep pulling data out of it. capture is that something. It is a loop: wait for the next chunk, store it, repeat until the pipe reports end-of-file (every writer has closed it). One loop watches stdout and another watches stderr, and both run while the command runs.

// the heart of capture(), simplified
for (;;) {
  const { done, value } = await reader.read()   // wait for the next chunk from the pipe
  if (done) return                              // end-of-file: nobody can write any more
  const room = max - size                       // how much of the 16 KiB is left
  if (room > 0) keep(value.subarray(0, room))   // store the part that fits
  if (value.length > room) truncated = true     // anything past that is dropped
}

Why not just read everything after the command finishes?

Because of the small bucket. When it is full, the command's next write blocks: the command goes to sleep until someone makes room. If the harness waited for the command to exit before reading, the command would be asleep waiting for room and the harness would be waiting for the command. Neither moves. Reading has to happen at the same time as running.

Why truncate at 16 KiB?

Output can be unlimited. cat on a huge log, or yes, which prints forever. Whatever the harness keeps ends up in three places: the harness's memory, the model's context (every byte costs tokens and can overflow the context window) and the log file. A cap of 16 KiB per stream puts a ceiling on all three. The truncated: true flag tells the model that something was cut, so it can run a narrower command.

Why keep reading after the cap?

This is the subtle part. It would seem simpler to stop reading once 16 KiB is stored. But then nobody empties the bucket, it fills, and the command blocks and hangs until the 30 second kill. So capture keeps emptying the pipe and throws the extra away. The command never finds out. It runs to the end, and the model gets the first 16 KiB plus the flag.

Paths, symlinks and realpath

A symlink is a path that points at another path, like a shortcut. On macOS, /var is a symlink to /private/var, and os.tmpdir() returns a path that starts with /var/folders/….

Seatbelt matches the resolved path, the one the kernel ends up at after following every symlink. A rule written with the shortcut spelling would never match anything. realpath() asks the filesystem for the resolved spelling, and runSandboxed uses it on the project, temp and home folders before it builds the profile.

Reading a Seatbelt profile

A profile is an ordered list of rules. Each rule says allow or deny, for one kind of operation, optionally limited to certain paths. Two ideas explain every profile:

  • The last matching rule wins. That is why deny file-write* comes first and the exceptions after it.
  • The first rule is allow default. Everything is allowed until a later rule says otherwise. The harness lists what it takes away.

(subpath X) matches X and everything under it. (literal X) matches exactly X. (regex …) matches by pattern.

Try it: ask the profile a question

    Time limits, signals and the pipe that stays open

    A signal is a small message the kernel delivers to a process. Most can be caught or ignored. SIGKILL cannot: the process is ended on the spot. After 30 seconds the harness sends it to bash, and the result carries timed_out: true.

    Killing bash does not kill what it started. Suppose the command is sleep 100 & echo started. The shell finishes at once, but sleep inherited the pipe, so the pipe's write end stays open. A pipe only reports end-of-file when every writer has closed it. If the harness waited for end-of-file, it would wait 100 seconds. So after bash exits it gives the pipes 200 ms to finish and then stops reading.

    Glossary
    kernel
    The core of the operating system. The only code allowed to touch hardware directly.
    process
    A running program, started by a parent process.
    syscall
    A request from a program to the kernel, such as open, write or connect.
    exec
    Replace the program inside a process with a different one, keeping the same process.
    file descriptor
    The number a process uses to refer to an open file, pipe or device. 0, 1 and 2 are stdin, stdout and stderr.
    pipe
    A small kernel buffer that connects one process's output to another's input.
    EOF
    End-of-file. A read returns it when there is no more data and nobody can write more.
    signal
    A message from the kernel to a process. SIGKILL ends it immediately.
    symlink
    A path that redirects to another path.
    Seatbelt
    macOS's kernel sandbox. Its profiles are written in a Scheme-like language called SBPL.
    EPERM
    The error code for a refused operation, shown as "Operation not permitted".
